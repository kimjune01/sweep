## Issue Evidence Pack

The reporter compares two Reactant-compiled calls to:

```julia
function f!(out, c, scratch, A1, A2)
    scratch .= real.(c)
    LinearAlgebra.mul!(out, A1, scratch)
    scratch .= imag.(c)
    LinearAlgebra.mul!(out, A2, scratch, -1, 1)
    return nothing
end
```

Inputs differ only in how `c` is presented:

- Flat path: `c_flat = Reactant.to_rarray(c_cpu)` where `c_cpu::Matrix{ComplexF32}`.
- View path: `buf3d = Reactant.to_rarray(buf3d_cpu)` and `c_view = @view buf3d[:, :, 1]`, where `buf3d_cpu[:, :, 1] == c_cpu`.

Reported outputs:

- Canonical reproducer `M=560, N=3168, K=8, S=4`: `max|flat-view| = 6.866455e-5`.
- Sweep with `K=4, S=2`:
  - `M=16, N=32`: `0.0`
  - `M=32, N=64`: `9.536743e-7`
  - `M=64, N=128`: `0.0`
  - `M=128, N=256`: `4.7683716e-6`
  - `M=256, N=512`: `7.6293945e-6`
  - `M=560, N=3168`: `6.866455e-5`
  - `M=1020, N=5000`: `0.0001296997`

Reporter suspicion: flat and view paths produce different XLA IR, roughly plain transpose versus slice + transpose + reshape, changing GEMM blocking / FP rounding.

## Blind-Blind Pushout

### Hypothesis A

Generated by subagent `019e3c05-6713-7fa1-8ce2-2de6d008208c`.

Root cause: the view path preserves SubArray layout provenance into Reactant/XLA lowering, so `real.(c_view)` / `imag.(c_view)` are not normalized to the same logical 2D array expression as the flat `ConcretePJRTArray` path before `mul!`. XLA sees `slice + transpose + reshape` rather than a direct 2D transpose/copy-like operand, chooses different GEMM layout/blocking, and accumulates FP32 in a different order.

Proposed fix shape: canonicalize rank-preserving dense views before GEMM lowering, or insert an explicit materialization/copy barrier for known dense 2D views so XLA receives the same operand layout as the flat 2D path.

Next perturbation: compare flat, view, and force-materialized view, e.g. `copy(@view buf3d_cpu[:, :, 1])` or Reactant-native equivalent, then inspect whether the delta disappears and whether HLO converges.

### Hypothesis B

Generated by subagent `019e3c05-8485-70e3-8411-303740044a54`.

Root cause: Reactant lowers `SubArray` with layout-preserving view semantics that survive too long. XLA sees a different HLO graph and layout metadata for a numerically identical dense 2D operand, so it may pick a different GEMM/custom-call path, tiling, fusion boundary, or accumulation order.

Proposed fix shape: normalize `SubArray` operands before `mul!` lowering, specifically canonicalizing view/slice rank-dropping plus reshape/transpose chains before GEMM recognition. The goal is not global bit-identical GEMMs; it is avoiding Reactant-generated HLO differences for equivalent dense 2D BLAS operands.

Next perturbation: force the view to a plain dense 2D array before JIT, then compare against the flat path. If the delta remains, investigate deeper value layout/stride metadata or scratch aliasing.

### Where A and B Diverge

The two blind passes mostly converge. The unresolved divergence is not between root causes; it is in fix placement and interpretation:

- A allows a local `mul!`-adjacent materialization barrier if that is the first layer with enough semantics.
- B prefers canonicalization before GEMM recognition and warns against trying to make all XLA matmuls bit-identical.
- Both leave open whether this is a Reactant correctness bug requiring identical lowering for equivalent dense inputs, or a floating-point reproducibility artifact that should be tested with tolerance rather than forced bitwise identity.

This divergence is the next graph edge: determine whether Reactant promises equivalent lowering / numerically stable tolerance for flat arrays and dense views, or merely mathematical equivalence under FP32 reassociation.

### H2 - The two-step accumulate pattern amplifies ordinary FP32 GEMM order differences

- Status: open.
- Mode: abduction; confidence 70%.
- Hypothesis: `mul!(out,A1,scratch)` followed by `mul!(out,A2,scratch,-1,1)` makes two separate FP32 accumulation paths visible; a single GEMM or `beta=0` variant might shrink or remove the delta.
- Null: the delta appears in the first GEMM alone and does not depend on the beta=1 accumulation pattern.
- Perturbation: split the MWE into first real-part GEMM only, second imaginary GEMM only, and full two-step accumulate; compare flat/view deltas.
- Predicted trajectory: convergent if full two-step is largest but single-step still shows smaller deltas; divergent if only beta=1 path triggers differences.
- Kill condition: identical deltas in single-step and two-step variants kill amplification as a meaningful cause.
- Edge: if confirmed, tests should include both reduced and full SpeedyWeather-like patterns.

### H3 - This is acceptable FP32 backend algorithm variance, not a correctness bug

- Status: open.
- Mode: abduction / standards interpretation; confidence 45%.
- Hypothesis: XLA is free to choose different but mathematically equivalent matmul algorithms for different operand layouts; the observed delta is within expected FP32 error for these dimensions.
- Null: Reactant should preserve equivalent dense view behavior closely enough that this view-specific algorithm split is a bug, especially because non-Reactant and flat Reactant match.
- Perturbation: compare against CPU BLAS/non-Reactant, run Float64 if supported, and estimate error relative to operation count / norms; check Reactant docs/tests for exactness versus tolerance expectations.
- Predicted trajectory: convergent if error is bounded and Float64 shrinks materially; divergent against if existing Reactant tests assert flat/view equivalence tighter than observed.
- Kill condition: any existing Reactant convention that treats dense view and flat input as equivalent under tight tolerances kills this as a ship-blocking explanation.
- Edge: documentation/tolerance if confirmed; canonicalization fix if killed.
